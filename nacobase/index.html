01执行摘要

首选 POC

NocoBase Professional

85 / 100 分

重视数据建模 + 插件扩展 + AI 增强，接受 $8K 商业授权和审批付费墙。

第二 POC

Joget DX Community

76 / 100 分

审批与数据量优先、零预算，接受 GPLv3 传染和表单驱动架构。

核心结论

  1. NocoBase 的「数据驱动 + 代码兜底」在架构层面被证实为先真实事实，非营销口号。微内核 + 全业务插件化 + 独立 npm 包 + 正式生命周期 API + 数据模型与 UI 解耦——这是本次调研中扩展性与数据建模最可验证的候选。但「AI 增强」的全面性需在 POC 中实测。
  2. 最大的决策变量是审批付费墙。NocoBase 3 社区版仅含单人审批，你的硬性审批需求（会签/或签/条件路由/转办/加签）全部落在 Professional Edition（$8,000 一次性终身许可）。Joget 社区版（GPLv3）免费、不限用户、原生 BPM，是唯一在审批层面有硬证据的替代方案。
  3. 其他 8 款候选产品无一通过四项硬性指标的同时筛选。淘汰的核心原因高度集中：审批缺失（ToolJet、Baserow、Directus）、插件不满足（简道云、Appsmith）、社区版不实用（明道云 30 人上限）、或者项目活跃度存疑（Corteza 2025 全年无 release）。

NocoBase 的实际竞争力

NocoBase 在数据建模（15/15 维度完全满足）、插件架构（19/20，本次调研最强）、以及 AI 能力（4/5，社区版免费且成熟）三个方面建立了明确优势。唯一短板是审批需要商业授权。如果你的组织对开源许可证宽松度（Apache-2.0）、架构扩展性和「低代码退路到代码」有较高要求，NocoBase 是当前证据支持下最契合的产品。

推荐的最终决策路径

  1. 先用 NocoBase 社区版验证：数据建模、插件开发流程、Departments 组织架构、AI 员工与 AI Builder。
  2. 采购 Professional 后验证审批：确认会签、条件路由、转办、加签在实际业务中的配置体验。
  3. 同时搭建 Joget 社区版作为对照：重点对比审批体验、组织架构数据权限粒度和表单驱动模式下的建模效率差异。
  4. 根据 POC 数据做最终选择，而非在调研阶段直接决定。

产品架构与设计理念

NocoBase 采用微内核架构——核心仅负责插件生命周期调度、依赖管理与基础能力封装（数据库适配器、认证引擎、ACL 引擎、资源路由、队列等），用户、权限、组织、工作流、数据源、审批等全部业务功能以插件形式实现。这使得「代码兜底」落在可替换的插件层而非核心层，开发者不需要修改平台核心源码即可扩展业务能力。

技术栈：TypeScript 全栈、Node.js 服务端 + React 前端、Sequelize ORM，数据库方言支持 SQLite / PostgreSQL / MySQL / SQL Server / Oracle（后两者仍为 0.1.0-beta.x）。

「数据驱动」体现：官方 README 明确表述 "Data-model driven, with data decoupled from UI. Business data stays in standard relational structures, separate from the UI"。数据模型是独立概念层，同一个 Collection 可绑定多个页面、表单、流程。

证据：github.com/nocobase/nocobase ｜ nocode.docs.nocobase.com/plugin-development ｜ nocobase.com/core

插件扩展机制 — 评分 19/20

NocoBase 在插件架构上是本次调研中证据最充分、体系最完整的候选：

  • 独立 npm 包：客户端插件继承 @nocobase/client-v2 Plugin 基类
  • 正式生命周期：afterAdd() → beforeLoad() → load() 固定执行顺序，每步有源码级证据
  • 扩展范围：数据模型、业务逻辑、工作流节点、页面组件、操作按钮、数据源连接器、ACL、迁移、i18n、定时任务
  • 插件管理：CLI 安装/卸载、浏览器管理器启用/禁用、版本升级
  • SDK 级接口：官方插件开发文档详述客户端与服务端扩展 API

唯一减分项（-1）：v2→v3 第三方插件跨大版本迁移的官方专项指南未发布（v3 仍 Beta），升级兼容性需在 POC 中验证。

关键判断

  1. NocoBase 的数据模型与 UI 解耦是架构层面的护城河——这使得同一条数据可以驱动多个页面、表单、流程，也使得插件可以通过扩展 Collection 而非修改页面来影响全局行为。Joget 的表单驱动模式在这个维度是架构级劣势。
  2. Joget 的组织架构模型更完整——Organization/Department/Grade/Employment/HOD/reportTo 是平台一等公民对象，而 NocoBase 的 Departments 仅是部门树。对「多组织机构」这个硬性需求，Joget 有原生优势。
  3. 两者在插件扩展的「非侵入性」上都满足要求，但路径不同：NocoBase 走 npm 生态 + TypeScript 全栈；Joget 走 Maven + OSGi + Java。前者对现代 Web 开发者更友好。

验收标准

  • 以上 10 项全部通过
  • 审批流程从创建到测试完成 ≤ 3 小时/场景
  • 组织架构配置 + 行级权限验证 ≤ 2 小时
  • 自定义 Process Tool 插件从脚手架到安装使用 ≤ 8 小时

可能的技术难点

  • Process Enhancement Plugin 虽是免费但文档标注 "designed for DX Enterprise & Professional"，实际功能在社区版是否受限需实测
  • JDBC 外部数据库为企业版，POC 只能用 REST API 替代
  • 加签功能待验证（文档未见），可能需要 BeanShell 自定义
  • Java/OSGi 开发环境搭建对不熟悉 Java 栈的团队有学习成本

重点验证

  1. Joget 大版本升级（如 DX 8→9）插件兼容性——如有 DX 8 和 9 环境，验证同一插件是否需要重新编译
  2. 数据跨表单一致性问题——在多个审批场景中验证数据是否保持一致
  3. GPLv3 传染性在插件场景的实际影响——咨询法律意见

13调研方法说明

本报告基于以下方法体系：

  1. 多代理联网核查：每个候选产品独立派发调研代理，强制使用官方来源（官网、官方文档、GitHub 仓库、LICENSE 文件、定价页），禁止编造功能、版本、价格、许可证。
  2. 3 票对抗验证：每条关键论断由 3 个独立验证代理进行对抗性核验（尝试反驳），需 ≥2 票支持方确认，1-2 票或 0-3 票的论断被否决或降级。
  3. 深度缺口补充：对入围产品 6 项已知缺口进行二次联网深挖，确保审批细节、许可证条款、价格、升级兼容性等决策关键信息有官方来源证据。

所有关键结论附官方来源链接（可直接访问验证）。无官方证据的项明确标注「待验证」，未编造价格、版本、功能或任何未经证实的信息。
